# ARCH-004 — Data architecture

How the domain model of `10-domain/` becomes a schema, and the conventions that
make its guarantees structural rather than remembered.

## 1. Table classes

Every table is assigned one class at design time, recorded in the module ledger
(`DOM-012-A`). A table whose class is unclear is a design that is not finished.

| Class | Rule | Examples |
| --- | --- | --- |
| **Ledger** | Append-only. No `UPDATE`, no `DELETE`. Corrections supersede. | marks entries, payments, journal lines, issued documents, role grants, audit |
| **Versioned** | Effective-dated rows; editing writes a new version | org units, schemes of study, fee structures, policies, templates |
| **Mutable** | Ordinary update and delete | draft applications, unsent notices, saved filters, preferences |

Append-only is enforced by database triggers, not by application discipline. A
`DELETE` against a ledger table fails at the database.

## 2. Tenant column and isolation

Every tenant-scoped table carries `institution_id`, indexed first in every
composite index, with a row-level security policy reading the tenant claim from
the transaction's session context.

The enumerated exceptions are `DOM-010 §3` and nothing else. Adding one requires an
ADR.

## 3. Effective dating

Versioned tables carry `effective_range tstzrange` with an exclusion constraint so
overlapping versions of the same logical row are impossible to insert. This is why
"which grading scheme applied in March 2025" is a query rather than an
investigation.

Historical records capture the version identifier they were computed under, or
enough context to resolve it deterministically by date (`DOM-003-E`).

## 4. Identifiers

Primary keys are UUIDv7 — sortable by creation time, no sequence contention across
tenants, and no information leaked about another institution's volume.

Human-facing identifiers — admission numbers, registration numbers, challan
references, verification codes — are separate columns generated by the `rules`
module from institution policy (`DOM-004-F`), unique within their stated scope,
and never used as primary keys.

## 5. Money and numbers

Money is `numeric`, never a float, with the currency stored alongside. Percentages
and marks are `numeric` with explicit scale; rounding is a policy decision
(`DOM-007-Q`) applied at computation, never a property of the column type.

## 6. Typed absence

`NULL` never means zero. Marks carry an explicit state — recorded, absent, not
appeared, exempted, withheld, pending — and aggregations must handle each
explicitly (`DOM-007-E`). A `SUM` that silently treats absence as zero is a defect,
and the query-discipline gate looks for it.

## 7. Sensitive fields

National identifiers, guardian contact details, and payroll amounts are encrypted
at the column level, never logged, never part of an index that would leak them, and
returned masked unless a capability explicitly permits otherwise — with that access
audited (`DOM-011-F`).

## 8. Migrations

Plain SQL, forward-only, one concern per migration. A migration that creates a
tenant-scoped table creates its RLS policy in the same migration; the structure
gate fails the build otherwise. Indexes on large tables are built concurrently. An
applied migration is never edited.

## 9. Projections

Read models — dashboards, defaulter lists, result sheets, attendance summaries —
are projections built from ledgers and events, and are always rebuildable from the
record (`DOM-012` §Projection). A projection is never the source of a number a user
sees; it is a cache of one the metric layer defines (`DOM-013`).
